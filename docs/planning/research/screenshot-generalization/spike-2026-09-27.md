## Spike A（延后至 Task 5）：WGC 窗口帧几何口径

### 方法

原简报的 Step 1：对 `tests/TestData/UiSampleApp/UiSampleApp.exe` 主窗，分别取三者的宽高坐标并打印对照：

1. WGC 首帧尺寸（现路径：`WgcCapture` 的 `item.Size` → `SoftwareBitmap` → PNG 解码后的 `Bitmap` 像素尺寸）；
2. `GetWindowRect(hwnd)`（现 `ScreenCapture.GetWindowInfo` 采用，含不可见 resize 边框/阴影余量）；
3. `DwmGetWindowAttribute(hwnd, DWMWA_EXTENDED_FRAME_BOUNDS=9)`（可见帧，Task 5 §Step 3 将采用）。

**本次未执行。** 该 spike 需要抓取真实 GUI 窗口（起 `UiSampleApp`、跑 WGC，甚至为对照打印临时程序 `dotnet run`），而用户此刻正在使用本机桌面，跑截图/抓屏极易受前台窗口、锁屏、DPI 影响而失败或产生噪声；且依赖真实 GUI 的结论本就该在具备真实 GUI 验证条件的任务里产出。

### 延后原因

- 需要真实 GUI 会话与真实窗口帧，属于「运行期几何实测」，不适合在用户占用桌面的时间窗做。
- 该结论**只被 Task 5 消费**（`CaptureWindow` 整窗几何「改用 Spike A 结论」——计划 L376），不阻塞 Task 3/4/6/10，延后无级联阻塞。
- Task 5 自身就要起 `UiSampleApp` 做 `WindowBounds_Relation` 测试（计划 L352-364），把几何实测并入同一真实 GUI 窗口最自然、成本最低。

### Task 5 必须得出的结论（交接清单）

- **WGC 首帧的像素尺寸 == `GetWindowRect` 尺寸，还是 == `DWMWA_EXTENDED_FRAME_BOUNDS` 尺寸？**（以及两者若不等，差值是四边对称的 DWM 阴影/边框余量，还是仅底/右多出的边框）。
- **WGC 帧左上角对应的屏幕坐标**：等于 `GetWindowRect.Left/Top` 还是 `EXTENDED_FRAME_BOUNDS.Left/Top`？这决定 `CaptureWindow(hwnd, clientArea=false)` 整窗出图时 `OriginX/OriginY`（Task 3 坐标模型）与「窗口帧裁剪窗口」的偏移量。
- 落点：把结论写进 `ScreenCapture.CaptureWindow` 的注释（计划 L376 要求「写注释记录结论」），并据此确定 Task 5 是否需要在裁剪时扣掉扩展边框偏移。

### 对哪个 Task 的影响

- **Task 5**（阻塞项，唯一直接消费者）：整窗几何换算与 `OriginX/OriginY` 基准。
- **Task 6 元素裁剪**：`CaptureElement` = 先拿窗口帧 → `rectPx` 减窗口帧原点 → 求交裁剪。窗口帧原点口径错，元素裁剪就会整体偏位。
- **Task 3**：`OriginX/OriginY` 若非 `GetWindowRect` 左上，则 Task 3 需知道窗口帧坐标系与虚拟屏坐标系的转换基准。

## Spike B：Engine 去 `System.Drawing.Common`

### 方法

对 Engine 全库静态检索 `System.Drawing`，并区分 `Capture/` 内外；同时核查移植相关的其它隐式依赖（WinRT 投影、`AllowUnsafeBlocks`）。

```powershell
Select-String -Path "src\DotNetDebugger.Engine\**\*.cs" -Pattern "System\.Drawing"
# 追加核查（非 Capture 文件里是否还有 WinRT/Drawing/unsafe）
Get-ChildItem -Recurse -Filter *.cs -Path src\DotNetDebugger.Engine |
  Where-Object { $_.FullName -notmatch '\\Capture\\' } |
  Select-String -Pattern "System\.Drawing|Windows\.Graphics|Windows\.Media|WinRT|\bunsafe\b|fixed\s*\("
```

### 观测（输出摘要）

命令一命中 **全部位于 `Capture/`，共 5 个文件**：

| 文件 | 命中 |
|---|---|
| `Capture/CaptureModels.cs` | `using System.Drawing;`（`Rectangle` 字段类型） |
| `Capture/GdiCapture.cs` | `using` + `new Bitmap(...)` ×3（`Format32bppArgb`） |
| `Capture/ImagePipeline.cs` | `using System.Drawing` / `.Drawing2D` / `.Imaging`（缩放/编码/纯黑） |
| `Capture/ScreenCapture.cs` | `using` + `new System.Drawing.Rectangle(...)` ×2 |
| `Capture/WgcCapture.cs` | `using` + XML 注释里的 `System.Drawing.Bitmap` |

命令二：**非 Capture 的 27 个 `.cs` 文件，`System.Drawing` / `Windows.Graphics` / `Windows.Media` / `WinRT` / `unsafe` / `fixed` 命中数 = 0**。

csproj 侧（`src/DotNetDebugger.Engine/DotNetDebugger.Engine.csproj`）：
- `<PackageReference Include="System.Drawing.Common" Version="10.0.12" />`（L24）；
- `<AllowUnsafeBlocks>true</AllowUnsafeBlocks>`（L8）——注释明确写「ImagePipeline.IsAllBlack 的指针逐像素扫描」，仅服务于 Capture。

### 结论

- **迁出 `Capture/*` 后可安全移除 `System.Drawing.Common` 包引用**：Engine 其余部分（DebugEngineCore/会话/单步/模型等 27 文件）零 `System.Drawing`、零 WinRT 投影依赖。
- 附带结论：`AllowUnsafeBlocks` 同样只在 Capture（`ImagePipeline.IsAllBlack` 指针扫描）使用，**迁移后可一并从 Engine csproj 删除**（迁移到 `SharpSight.Capture` 的新 csproj 需保留）。
- 与预期一致，无「Engine 别处也用 System.Drawing」的反例。

### 对哪个 Task 的影响

- **Task 1（抽出 `SharpSight.Capture`）**：迁移清单确认是「`Capture/` 5 文件 + `System.Drawing.Common` 包引用 + `AllowUnsafeBlocks`」三件套一起去 Engine；新库 csproj 承接二者。
- **Task 7（双轴降采样）/ Task 8（WebP）**：`System.Drawing.Common` 依赖现落在新库，ImageSharp WebP 亦加在新库，Engine 不受影响。
- 文档同步项：Task 11 需更新 `src/DotNetDebugger.Engine/AGENTS.md`「边界纪律」中 `System.Drawing.Common 10.0.12` 一句与根 `AGENTS.md` 依赖方向说明（spec §降级清单 L273 已列）。

## Spike C：2MB 与默认目录测试 seam

### 方法

读四处实现/测试，确认阈值分支与默认目录是否可测、缺口在哪：
`tests/DotNetDebuggerMcp.Tests/ScreenshotToolTests.cs`、`src/DotNetDebuggerMcp/Tools/Debugger/DebugScreenshotTool.cs`（2MB 落盘分支 113-136 行）、`src/DotNetDebuggerMcp/Configuration/AppConfig.cs`（`InlineImageBase64Bytes`）、以及旧 spec §5.1（L188）与 `AppServices.ConfigureForTest/ResetForTest` 既有测试注入范式。

### 观测（现状）

- **阈值分支**（`DebugScreenshotTool.cs:113-114`）：
  ```csharp
  var b64Len = ((long)result.Image.Length + 2) / 3 * 4;
  var wantFile = !string.IsNullOrWhiteSpace(filePath) || b64Len >= AppConfig.InlineImageBase64Bytes;
  ```
- **默认目录分支**（`DebugScreenshotTool.cs:194/197`）经 `AppConfig.ScreenshotsDir`（`ResolveScreenshotPath` 内 `Directory.CreateDirectory` + `Path.Combine`）。
- `AppConfig.InlineImageBase64Bytes` 现为 **`public const long = 2*1024*1024`**（`AppConfig.cs:41`）——**`const` 会被编译期内联进 `DebugScreenshotTool`**，运行时无法替换。
- `AppConfig.ScreenshotsDir` 现为 **`public static readonly string`**（`AppConfig.cs:47`）——`readonly` 亦不可测期重定向。
- 既有测试只覆盖 **`filePath` 强制落盘分支**（`ForcedFilePath_WritesFile_NoImageBlock`）与 **`ResolveScreenshotPath` 纯函数路径模式**（`ResolveScreenshotPath_DefaultDirPattern_And_FilePathOverride`，断言以 `AppConfig.ScreenshotsDir` 开头）；**没有任何测试触发「图片 ≥2MB → 自动落盘默认目录」分支**。
- 旧 spec §5.1（L188）明确记载缺口：「默认目录分支触发需 2MB 阈值常量具备测试可替换 seam（internal/参数注入，实现时定）」。
- `ScreenshotToolTests.cs:14` 的类注释写着「类内静态 seam（`InlineImageLimitBytes`）」——但除该注释自身外，实现在 `src/`、`tests/` 内检索该名称 **0 命中**：这是一个**计划过、从未实现的悬空 seam**（注释与代码不符，属历史遗留噪声）。

### 结论：seam 方案（推荐）

采用 **AppConfig 可注入静态字段 + `ConfigureForTest/ResetForTest`**（与宿主既有 `AppServices` 测试注入范式同构），理由：调用点名称不变、不动 MCP 工具签名、能同时覆盖「阈值」与「默认目录」两个不可控点。

**改动成员（仅内宿主程序集，`InternalsVisibleTo DotNetDebuggerMcp.Tests` 已存在，csproj L66）：**

1. `AppConfig.cs`：
   - 新增 `public const long DefaultInlineImageBase64Bytes = 2 * 1024 * 1024;`（保留具名默认值供文档/自检引用）。
   - 把 `InlineImageBase64Bytes` 由 `const` 改为 **`internal static long InlineImageBase64Bytes = DefaultInlineImageBase64Bytes;`**（可写字段；**调用点文本不变**，宿主 L114 无需改）。
   - 把 `ScreenshotsDir` 由 `static readonly` 字段改为 **属性**：`private static readonly string DefaultScreenshotsDir = Path.Combine(...);` + `internal static string? ScreenshotsDirOverride;` + `public static string ScreenshotsDir => ScreenshotsDirOverride ?? DefaultScreenshotsDir;`（**调用点文本不变**，L194/197 与测试 L261 无需改）。
   - 新增注入/复位（对齐 `AppServices`）：
     ```csharp
     internal static void ConfigureForTest(long? inlineImageBase64Bytes = null, string? screenshotsDirOverride = null)
     {
         InlineImageBase64Bytes = inlineImageBase64Bytes ?? DefaultInlineImageBase64Bytes;
         ScreenshotsDirOverride = screenshotsDirOverride;
     }
     internal static void ResetForTest()
     {
         InlineImageBase64Bytes = DefaultInlineImageBase64Bytes;
         ScreenshotsDirOverride = null;
     }
     ```
2. 无需改 `DebugScreenshotTool`（两处名称引用保持有效）。

**新增测试（`ScreenshotToolTests`，同 `[Collection("AppServices")]`，串行）：**

```csharp
[Fact]
public async Task AutoFallback_OverThreshold_WritesDefaultDir_NoImageBlock()
{
    var dir = Path.Combine(Path.GetTempPath(), $"screenshot-autofallback-{Guid.NewGuid():N}");
    AppConfig.ConfigureForTest(inlineImageBase64Bytes: 1, screenshotsDirOverride: dir);
    await using var mcp = await DebugMcpToolsTests.ConnectAsync();
    using var app = LaunchUiSampleApp();
    try
    {
        var r = await DebugMcpToolsTests.CallAsync(mcp, "screenshot", new Dictionary<string, object?>
        { ["processId"] = app.Id, ["timeoutSeconds"] = 5 });
        Assert.True(r.IsError != true, r.Text());
        Assert.Single(r.Content);                       // 阈值触发 → 仅文本，无 image 块
        Assert.Contains("已落盘: ", r.Text());
        var file = /* 从头部解析出的绝对路径 */;
        Assert.StartsWith(Path.GetFullPath(dir), file);
        Assert.True(File.Exists(file));
        Assert.True(File.ReadAllBytes(file).AsSpan(0, 8).SequenceEqual(PngMagic));
    }
    finally
    {
        KillUiSampleApp(app);
        AppConfig.ResetForTest();
        try { Directory.Delete(dir, true); } catch { /* 忽略 */ }
    }
}
```

**对现有测试的影响：** 无破坏性影响——两个调用点名称保留，`ResolveScreenshotPath_DefaultDirPattern_And_FilePathOverride` 在默认值（override=null）下行为与断言不变。唯一纪律约束：override 是进程级静态状态，**必须**在 `try/finally` 中 `ResetForTest`；本类已在 `[Collection("AppServices")]`（串行），不跨类污染。

**被否方案：** 给工具方法加 `internal` 重载参数——会与 MCP 暴露签名纠缠（SDK 按方法签名生成工具面），且无法干净地覆盖 `ResolveScreenshotPath` 内部的默认目录常量；不采用。

**顺带建议（Task 10 落地时清理）：** 把 `ScreenshotToolTests.cs:14` 的「`InlineImageLimitBytes`」悬空注释改为实际 seam 名（`AppConfig.ConfigureForTest`），消除注释-代码不符。

### 对哪个 Task 的影响

- **Task 10（宿主工具面，含测试）**：本 seam 是 spec §11-7「2MB/默认目录分支可替换 seam」的落地方案；Task 10 重写工具面时把该测试补进 `ScreenshotToolTests`。
- **Task 7（默认 1568 / 双轴降采样）**：`AppConfig` 会因新增 `MaxWidth/MaxHeight` 默认值同时被改（计划 L447），两种改动应协调到同一批 `AppConfig` 编辑，避免冲突。
- **Task 11（回归）**：seam 是宿主工具单测「落盘/2MB seam」条目的前置（spec §6.4 L294）。
