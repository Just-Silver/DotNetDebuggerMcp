# Spec · V3 日志+事件统一时间线

> 状态：**计划中（草案）**——三源结构已查证，供后续实施直接参照。实施前置：按宿主 TODO「agent 自动化调试闭环缺口清单」立项确认后补取舍点拍板。
> 关联：宿主 TODO V3；依赖 P1 输出时间戳（已完成）；是 V2（崩溃 dump）的前置——崩溃前"最后 N 条 timeline"比裸 dump 更有复盘价值。

## 1. 背景与目标

agent 复盘调试过程时常要拼因果链：**「先 A 日志 → 命中 B 断点 → agent 改值 → 再 C 异常」**。现状三源各自隔离：`debug_output` 只给目标日志尾部、`debug_state` 只给最近停点、`debug_wait` 附 trace 轨迹——没有一个命令能按时间看到完整经过。目标：一条 `debug_timeline` 命令，按时间对齐输出 目标日志 ↔ 调试事件 ↔ agent 动作。

非目标：细粒度指令级时间线（本工具是秒级/毫秒级复盘，不是 profiler）；Web 端新 UI（agent 是主消费者，文本输出即可）；V2 的自动 dump（只做"现在能查到什么"，不做"崩溃时自动留什么"）。

## 2. 三源现状（起草时已查证，2026-09-08）

| 源 | 载体（record） | 时间戳 | 缓冲 | 现状可用性 |
|---|---|---|---|---|
| **目标日志** | `ProcessOutputLine(Sequence, Timestamp, Stream, Text)` | ✅ `DateTimeOffset`（Append 入口锁外取本机时刻） | `ProcessOutputCapture` 环形 2000 行 + `Tail(maxLines, filter)` | ✅ 直接用 |
| **agent 动作** | `AgentAction(Sequence, UtcTimestamp, Tool, ArgsSummary, ResultSummary)` | ✅ | `AgentActionLog` 环形 1000 + `Snapshot()` | ✅ 直接用 |
| **调试事件** | `DebugEvent(SessionId, Sequence, UtcTimestamp, Kind, Payload)` | ✅ 事件本身带 | ❌ **`SessionEventBuffer` 只折叠成"最新快照"，不保留事件历史** | ⚠️ 最大缺口 |

### 关键缺口（V3 真正的工程量所在）

`SessionEventBuffer.OnEvent`（SessionEventBuffer.cs:151）对 BreakpointHit/StepCompleted/ExceptionHit 只更新 `_lastStop`（单条覆盖），**历史被丢弃**；TraceHit 进独立 `_traces` 环形（100 条，消费式）。因此 timeline 若只聚合现有缓冲，只能看到：
- 日志（有历史）✅
- agent 动作（有历史）✅
- trace 轨迹（有历史，100 条）✅
- **断点命中/异常/step 历史** ❌（只有最近一次）

**结论**：Session 需新增「调试事件历史环形缓冲」，把关键事件在折叠的同时另存一份。

## 3. 分层设计

### 3.1 Session 侧：事件历史缓冲 + 归并

在 `SessionEventBuffer` 内新增（或独立 `DebugTimelineBuffer` 组件）：

1. **事件历史环形缓冲**（建议 500 条）：`OnEvent` 消费 `DebugEvent` 流时，除现有折叠逻辑外，把 `Kind ∈ {BreakpointHit, StepCompleted, ExceptionHit, ExceptionSkipped, TraceHit, SessionStateChanged, EngineLog}` 的事件**原样**（`DebugEvent` record 已带 UtcTimestamp/Sequence，零改动）追加进历史缓冲。TraceHit 已有独立轨迹缓冲——两条路并存（timeline 用历史、debug_wait 消费式轨迹保留给现有语义），或在历史里只存引用。**复用现成 DebugEvent，不改 Engine。**
2. **渲染归一**：每源产出一行统一文本（时间 + 源标记 + 摘要）：
   ```
   [12:00:01.234] log   Started listening on :5000          ← ProcessOutputLine
   [12:00:03.102] bp    breakpoint 3 @ WorkScores (t=8)      ← DebugEvent(BreakpointHit)
   [12:00:03.105] step  step completed                        ← DebugEvent(StepCompleted)
   [12:00:03.110] act   debug_evaluate "i == 3"               ← AgentAction
   [12:00:03.205] trc   bp5 i=3 ...                           ← TraceHit
   [12:00:04.001] exc   exception System.Exception: boom      ← DebugEvent(ExceptionHit)
   ```
   事件摘要从现有 Payload 提取（BreakpointHitPayload 等 record 字段现成）。
3. **暴露**：`GetTimeline(int limit, TimelineFilter?)` → 归并排序后的统一行列表。归并 = 按 `UtcTimestamp` 排序；同毫秒/同刻打平靠各源 `Sequence`（都是进程内单调递增）。**时钟一致性**：三源在同一 MCP server 进程内取 `UtcNow`，天然同钟，无需跨钟校正。

### 3.2 宿主侧：`debug_timeline` 工具

```
参数：lines（默认 100，取最近 N 条，遵守输出分页约定）
      filter=""（子串过滤，如 filter=exception / filter=WorkScores）
      kind=all|log|bp|exc|step|trc|act（可选，按源筛选）
返回：统一时间行 + 分页头（头部：目标 pid / 时间范围 / 总量）
```

### 3.3 线程/容量纪律

- 环形缓冲上限防 token 失控（500 事件 + 现有 2000 日志 + 1000 动作，均内存常驻——debug_timeline 拉取时归并，无新后台任务，复用 SessionEventBuffer 既有消费线程）。
- `lines` 默认倒序取最近 N（复盘"最近发生了什么"），支持 `lines="start-end"` 翻页（遵守输出约定）。

## 4. 取舍点（立项时拍板）

1. **事件历史容量**：500 条是否够（覆盖"最近几分钟调试"）？与日志 2000/动作 1000 是否对齐？
2. **agent 动作是否入 timeline**：建议入（因果链一环——agent 做了什么导致后续现象），但用 `act` 前缀 + 可 `kind` 排除。
3. **TraceHit 双轨**：现有 `_traces`（消费式，供 debug_wait 折叠反馈）与 timeline 历史并存，还是 timeline 统一接管？**建议并存**（各自语义独立，改动最小），timeline 历史里放 TraceHit 引用/轻量摘要。
4. **展示粒度**：高频日志（Web 每 100ms 一条）会刷屏——`lines` 倒序 + `filter` 已缓解；是否需"事件聚合折叠"（连续同类折叠为 N 条）？建议 v1 不做（输出分页已够），留待真实反馈。
5. **停点语义细分（DebugMCP 借鉴，DB-参考）**：DebugMCP `waitForDebugSessionReady` 区分 stopped/attached/terminated/no-session/timeout，且 **attach 到长活进程即成功态**（不会自己停，等栈帧会烧光超时）。timeline/debug_wait 的状态描述可吸收该"attach 即成功"语义与五态措辞——**尤其 attach 场景「已附加但进程继续跑（无停点）」应明确提示，而不是看起来像卡住**（对照 R2/R3 attach 反馈）。

## 5. 验证方案

- **Session 纯内存单测**（无真实进程，可快速跑）：三源混合注入 → 断言归并时间序、kind 过滤、limit 截断、filter 子串。
- **宿主 e2e**：debug_launch DebugTarget → 打 trace 断点 + 触发异常 → `debug_timeline` 输出含 log/bp/trc/exc 行且时间有序。
- **回归护栏**：timeline 返回格式断言（V4 语料测试预留挂接）。
