# Spec · W1 现场改写（SetValue 后继续）

> 状态：**已立项**（2026-09-09 拍板；2026-09-09 spike 实测定案支持矩阵——见 §7）。三项取舍：① v1 覆盖 = 三层全含（确定项 + 数组元素/对象内 struct 字段承诺项，spike 首任务通过即实现、失败降级提示）；② 引用型目标含**对象重定向**进 v1（源 = 另一条路径解析的引用地址）；③ 新值按目标类型转换（value 文本扩展小数文法）。实施计划见 `docs/planning/plans/2026-09-09-w1-set-value.md`，规格冻结。
> 关联：宿主 TODO W1；复用 P6/P7 路径求值链（`ReadPathValue`/`EvaluatePathAsync`）；参考 dnSpyEx `DbgValue.SetValue`（本地 `../../Externals/DebuggerExternals/`）。

## 1. 背景与目标

agent 调试的经典实验是**「把 X 改成 Y 再跑，看是否复现/消失」**（二分定位）。现状 `debug_variables`/`debug_evaluate` 全部只读——停点后不能改任何值就得 continue，改配置要重启进程（重来一遍启动时序）。目标：停点后改写**局部变量/参数/对象字段/数组元素**的值，再 continue，观察行为变化。

对标：VS 调试器「编辑值后继续」（watch 窗口改值 / 即时窗口赋值）。但我们的 agent 场景是**文本协议**：给路径+新值文本，返回「原值→新值」确认。

非目标：构造新对象实例（需 func-eval `Eval2.NewObject`，危险且 async/UI 目标会死锁——I 项已关）；改字符串内容（需新建字符串，同属 func-eval）；改 readonly/const 字段；改静态只读。这些 v1 明确不支持并给中文提示。

## 2. 现状锚点（起草时已查证，2026-09-08）

| 设施 | 位置 | 与 W1 的关系 |
|---|---|---|
| `ReadPathValue(threadId, rootName, segments)`（同步，泵内直读） | `Engine/DebugEngineCore.cs:771` | 路径解析已通——逐段定位到目标值对象，**写只需在末段换成 SetValue** |
| `EvaluatePathAsync`（P6 对外门面，PostAsyncResult 投泵） | `DebugEngineCore.cs:459` | 写命令走同款「投泵→泵内同步执行→返回」通道 |
| `EvalValue.Raw`/`DebugEvalResult`（P6 求值结果容器） | Engine | 携带末段目标值对象引用 |
| 根名解析（locals/args 按名匹配 + slotN 回退） | Engine | 写目标同样需要「路径定位到值」——根 + 段 |
| 标量解析（数字/bool/枚举，统一 decimal） | Session `ExpressionParser` | 新值文本 → 目标类型转换复用它 |

### ClrDebug 写 API 查证结论（关键，已 grep 源码确认）

| 目标 | API | 是否已封装 | 说明 |
|---|---|---|---|
| **任意值对象（含栈上局部/参数）** | `CorDebugGenericValue.SetValue(IntPtr)` | ✅ `Value/CorDebugGenericValue.cs:59` | **这是 VS 改值的底层机制**——`ICorDebugGenericValue` XML 注释明言「applies to **all values**, provides **Get and Set**」；引用类型时值是引用本身（非内容）。栈上值类型局部经 `GetLocalVariable`/`GetArgument`（读 API 已封装）拿到值对象后**可直接 SetValue 写回**，无需帧级 Set 接口 |
| **值对象向下转型** | `corDebugValue.As<T>()` | ✅ `Extensions/Extensions.As.cs:200`（含 `As<CorDebugGenericValue>`/`As<CorDebugReferenceValue>`） | COM QI/包装构造，读链路拿到的是基类 `CorDebugValue`，写前转型用 |
| 引用重定向 | `CorDebugReferenceValue.SetValue(CORDB_ADDRESS)` | ✅ `Value/CorDebugReferenceValue.cs:72` | 引用型字段/局部置 null（地址 0）或重定向 |
| 数组元素 | `CorDebugArrayValue.GetElementAtPosition` | ⚠️ 读已封装（Value/CorDebugArrayValue.cs:249）；**元素 Set 依赖"元素 value 对象可写"**（同 GenericValue 路径，待 spike） | 见 §5 |
| 对象字段 | `CorDebugObjectValue.GetFieldValue` → 字段值对象 | ✅ 已封装且 Engine 在用（DebugEngineCore.cs:871） | 字段读已通，写 = 字段 value 对象 SetValue |

> **结论（修正）**：W1 可行面比初稿判断**更宽**——「栈上值类型局部/参数」也可改（`GetLocalVariable` 读 → `As<CorDebugGenericValue>().SetValue` 写），这正是 VS 改局部变量的实现路径。ClrDebug **不需要**帧级 `SetLocalVariable` 镜像，因为它从未封装（原生 ICorDebugILFrame 无此方法）——写局部本来就走值对象 SetValue。唯一保留的 v1 边界：**构造新对象/字符串内容**（需 func-eval，I 项已关）。

## 3. 目标工作流（agent 视角）

```
停点（断点/异常/单步）
  ↓
debug_set <路径> <新值>
  e.g. debug_set "scores[2]" 99        → 数组元素
  e.g. debug_set "i" 5                  → 栈上局部（值类型）
  e.g. debug_set "order.Total" 1000m   → 对象字段
  e.g. debug_set "config.Timeout" 0    → 对象字段
  e.g. debug_set "config" null         → 引用型局部置 null
  e.g. debug_set "cfg.Current" "cfg.Backup" → 引用重定向：指向同帧另一条路径解出的已存在对象
  ↓
返回「路径已改：原值 X → 新值 Y」（明示原值防误判）→ debug_continue
```

**铁律**：返回必须带**原值回显**（改前值 → 改后值）。改一个非因果变量会让 agent 误以为验证了假设——回显让 agent 能判断改写是否触及真正原因。

## 4. 分层设计

- **Engine**（`DebugEngineCore`）：新增 `WritePathValue(threadId, rootName, segments, newValue)` 同步方法（泵内），与 `ReadPathValue` 共用路径解析前段；末段分派：
  - 目标为 `CorDebugGenericValue`（值类型字段/局部/参数/数组元素）→ 标量解析字节 → `SetValue`
  - 目标为 `CorDebugReferenceValue`（引用字段/局部/数组槽）→ 置 null（SetValue(0)）或**对象重定向**：源 = 另一条路径解析得到的引用值（读源路径的引用地址 → SetValue(地址)；源与目标同帧解析）
- **Session**：新组件（或扩展 `ExpressionEvaluator`）解析新值文本 → **按目标运行时类型转换**（目标类型由引擎末段值对象 `ExactType` 提供——转换器在引擎泵内按类型分发，Session 只做文法/文本形态校验）。value 文法 = P6 字面量（int/string/bool/null）扩展**小数数字**（`1000m`/`0.5`/`-1` 等按目标数值类型解析）；字符串目标只能置 null（内容构造需 func-eval）；枚举按底层整数值。
- **宿主**：新工具 `debug_set`（读写分离，语义清晰）。参数：`path`、`value`、`threadId=0`（最近停点线程）。返回带原值。

## 5. 拍板记录与 spike 承诺（2026-09-09 用户拍板）

> 三项取舍已拍板：① 三层覆盖全进 v1；② 引用重定向进 v1；③ 新值按目标类型转换。下列 spike 均为**实施计划首任务**（TDD 先行实测），通过即实现、失败按「目标类型 v1 不支持」降级提示并保持读链路可用。

1. **数组元素写**（承诺 v1）：`GetElementAtPosition` 返回的元素 value 对象是否可直接 `SetValue` 写回（数组元素在堆上，理论上同 GenericValue 路径）——实施计划 Task 0 spike 实测。
2. **对象内 struct 值类型字段的写**（承诺 v1）：拆装箱边界（`As<CorDebugBoxValue>` vs `As<CorDebugGenericValue>` 取舍）——Task 0 spike 实测；失败则该项降级为「v1 不支持，提示用对象字段外层整体替换」。
3. **值类型局部写回**（承诺 v1）：`GetLocalVariable` 返回是否活引用（指向栈槽）——VS 实证可行，Task 0 在我们引擎 ILFrame + 停点线程实测确认（寄存器驻留/优化变量处理）。

**风险提示**：写进程内存永远有让目标崩的风险（尤其值类型写错布局）。v1 策略：只写「读链路已证明可定位」的目标；写后不校验（无法轻量校验），靠 agent 观察行为；`debug_set` Description/README 明示风险。

## 6. 验证方案

- **Engine 单测**：DebugTarget 新增改写目标（如字段 `_flag` 决定分支走向）；attach → 断点 → set 字段 → continue → 断言走另一分支。
- **Session 桩测试**：新值文本解析（合法/非法类型穷尽）+ 路径定位。
- **宿主 e2e**：`debug_set` 全流程（改前值回显、非法路径、readonly 拒绝、非 Stopped 拒绝）。
- 回归护栏：改值返回含「原值」断言（V4 语料测试预留挂接）。

## 7. 边界汇总（2026-09-09 拍板定稿；spike 实测支持矩阵 2026-09-09 落定，❌ 行即 v1 降级）

|---|---|---|
| 对象字段（值类型/引用） | ✅（spike 通过：h.N 对象 int 字段直写） | 改 readonly/const/静态只读 |
| **栈上值类型局部/参数** | ✅（spike 通过：参数写回活引用，读回一致） | — |
| **对象内 struct 值类型字段** | ✅（spike 通过：struct 字段终端为对象值，内层标量字段 GetFieldValue→GenericValue 直写，h.P.X 读回 7） | — |
| **enum 对象字段** | ❌ **v1 降级**（spike：h.Kind 字段终端为 `CorDebugObjectValue`（非 GenericValue），`As<CorDebugGenericValue>` 转换抛异常——enum 按元数据底层 TypeDef 表示；引擎给「目标类型暂不支持写」中文提示。v2 考虑经 `value__` 底层字段间接写） | 直接标量写 enum 字段 |
