- [ ] **C. `debug_stack` 帧名真名化（Engine+宿主｜方案已确认，B 的前置）**——实证 21 帧全 `模块!0x06000xxx+0x`，agent 要逐个 token 反查。**代码核查**：`DebugStackFrame` 已有 `TypeName`/`MethodName` 字段且 `GetStackFramesAsync` 已填充（DebugEngineCore.cs:431-435），但 `TryGetTypeName`(:1235)/`TryGetMethodName`(:1245) **只返回 token 十六进制**（未调 resolver）；宿主 `debug_stack` 渲染只用 `f.Location`（DebugInspectTool.cs:38），完全没用已填充字段。`TypeNameResolver`（classToken→全名）已具备；`SymbolNameResolver` 只有 ArgNames/LocalNames、**缺 ReadMethodName**。**方案（2026-09-07 定，agent 视角）**：① 引擎 `TryGetTypeName` 改调 `TypeNameResolver.Resolve(modulePath, classToken)`（类 token，路径从 `ilf.Function.Class` 或 module 得）、失败降级 token；`SymbolNameResolver` 加 `ReadMethodName(modulePath, methodToken)`（方法 token→md.Name）、`TryGetMethodName` 调它、失败降级 token；② 宿主 `debug_stack` 渲染优先 `类型.方法`（如 `CoreMes.ViewModels.MainViewModel.SwitchAutoState`），token 保留作辅助（行尾 `0x...`，agent 可用 token 下断点），无名字降级现状 `模块!token+offset`；③ **全部帧都真名化不折叠**（agent 需看全调用链判断跨 UI/异步边界，折叠丢信息）；④ **状态机类型名特殊处理为 B 铺路**：`<Foo>d__N` → 标注「(状态机) Foo」（从类名提取原方法名），`MoveNext` 帧显示「Foo (状态机).MoveNext」。**依赖关系**：C 是 B 的前置（B 的状态机识别/「对应 async 方法 X」备注依赖 C 的类型名解析）。**约束**：改 `TryGetTypeName`/`TryGetMethodName` 影响 Engine `StateReadTests`（现断言 token 文本，需同步）；`debug_stack` 输出格式变化影响宿主 e2e/Client 断言；R5 spec「帧名真名化」顺手项由此吸收。**与 ROADMAP「debug_stack 帧名真名化」顺手项同向并落地**。

- [ ] **E. `debug_breakpoint_set` 增 typeName+memberName 成员级定位（宿主｜方案已确认，agent 视角）**——实证下「手自动切换」断点路径长：XAML 找按钮→源码找命令方法→反编译拿 signature→才得 token 0x06000117。agent 最自然的表达是「在某某方法停」，现有三种定位（token/typeName+line/sourcePath+line）独缺成员级，被迫 decompile_member 拿 token 再 set（两跳）。**方案（2026-09-07 定，agent 视角）**：`debug_breakpoint_set` 增加 `typeName+memberName` 定位方式——内部复用 DecompileMember 的成员定位逻辑（`MemberResolver`）：单匹配直接设断点（返回断点 id，同 token 分支的 DescribeSet）；多匹配返回 `#MEMBER` 签名清单提示 agent 用 methodToken 精确重设（与 decompile_member 超限清单同款格式，token 可直接用于现有 methodToken 参数闭环）；未匹配返回未找到+相近名提示。目标 = agent 拿到「在某方法停」类任务时一步直达，免中间反编译往返。**取舍**：多匹配回退清单而非自动选（避免歧义静默错停）；memberName 匹配语义与 decompile_member 一致（子串/忽略大小写，重载并列）。**约束**：新定位分支在 typeName 非空+memberName 非空+line=0 时触发（不挤占现有 typeName+line）；复用 MemberResolver 需确认其 internal 可见性（宿主经 InternalsVisibleTo 已可访问）；README 断点定位方式表同步。**与 B/C 关系**：与 C（真名化）共用 token 解析设施，独立可做。
- [ ] **F. async 方法内 step 体验：收敛为「引导行断点直达」，不做引擎 prolog 聚合（Engine｜方案修正 2026-09-07）**——实证 step over 在 SwitchAutoState 连续 +0x0→+0x5→+0x6→+0xc→+0x11 逐 IL 走。**根因（修正，2026-09-07）**：不是「无 PDB」——CoreMes 有 PDB；是 step 落点在外壳方法状态机装配区/进 MoveNext，业务行序列点挂外壳方法 token，step 时视图钉在方法头 `{` 行不动。**结论：引擎聚合步进（R5 已整体跳过 async 单步）不再单独做**——B 已确立「async 用 typeName+line 行断点直达 + continue」为正确工作流（命中即渲染还原源码），step 走查 async 非 agent 正确路径。F 收敛为 B 的引导一部分（遇 async 帧提示改用行断点），无需独立引擎改动。
- [ ] **G. 状态机内部帧变量 `<>` 字段无业务语义（宿主｜定案 2026-09-07：并入 B，不单独立项）**——实证 step 进状态机后 `debug_variables` 只读 `<>1__state`/`<>t__builder`/`<>4__this`/`<>u__1` 编译器字段。**澄清（2026-09-07，「状态机内部无法调试还是无意义」）**：状态机内部**完全能调试**（MoveNext 是普通方法，可断点/单步/读变量），只是无对应 C# 源码可渲染（业务可读形态挂外壳方法还原）；**调试意义分层**——① 日常业务调试（某 await 是否执行/到哪）：走外壳还原源码行断点直达（B 主路径），状态机内部意义低；② 深入机制（状态机如何分派/当前进度/为何走 case N）：有意义，看 MoveNext IL + `<>1__state`（B 的 IL 兜底用途）；③ 反编译不可靠场景：IL 是唯一真相。**方案**：不单独做——并入 B 引导文案，状态机帧的 `debug_variables` 附一句「编译器内部字段（`<>1__state`=状态机进度，N 表示已过第 N-1 个 await）；业务值请 step out 回外壳方法/调用方看」。**与 B 关系**：G 的提示是 B 引导的一部分。

### 我的补充建议（2026-09-07，待探讨）

- [ ] **L. `debug_wait` 返回附带明确的「接下来建议动作」**——实证中停点返回后 agent 需自行决定 next（看栈/看变量/继续/单步）。若 wait/state 返回尾部带一句面向 agent 的推荐动作（如「已停：建议 debug_stack 看调用链 → debug_variables 看当前帧值 → debug_continue 放行」），可降低 agent 决策成本。与 ROADMAP「握手加调试操作序列」同向但下沉到每次停点。

- [ ] **O. `debug_launch` Description/返回状态准确性核对（宿主｜2026-09-07 发现）**——Description 是 agent 看到的工具契约，逐句核对实际行为发现 3 处：① **launch 返回 `当前状态：None`**（StateText 对 None 走 `_=>state.ToString()` 裸吐 "None"）与 Description「进程停在 Main 前」语义矛盾——原因是 Buffer 消费 Launching/Attaching 状态事件有异步延迟，Activate 时状态未追上，agent 会困惑（R3 修过 Attaching 但没处理 None）；② **`workingDirectory` 参数描述**「默认空=继承 MCP server 的当前目录」需随 D 同步为「默认空=exe 所在目录」；③ **launch 返回缺「实际生效工作目录」**（agent 无法感知目标产物写到哪，D 方案已含此项）。方向：① launch 返回前等待 Buffer 追上状态（或返回文本不依赖 Buffer 状态、直接按 launch 成功语义写「已冻结在 Main 前」）；②③ 随 D 一并处理。属 Description/文案准确性，改 Description 须同 commit 同步根 README 工具表。
